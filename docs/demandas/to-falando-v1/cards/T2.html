Origem

Demanda to-falando-v1: RF-2, RF-3; RN-1 a RN-4; CA-2 a CA-6.

Padrão

Técnica §3 (contratos de autenticação, erros { erro, mensagem }), §4 (usuarios, sessoes, configuracoes; migrations por PRAGMA user_version com backup), §6 (scrypt, token só com hash, safeStorage, limite de tentativas).

Implementação (04/11/2026, commit 4c7f728)

  • Rotas: POST /api/auth/cadastro (201 { token, usuario }; 400 dados_invalidos, 403 convite_invalido, 409 usuario_em_uso, 409 limite_contas, 429 muitas_tentativas), POST /api/auth/login (401 credenciais_invalidas, mesma resposta para usuário inexistente), POST /api/auth/sair (204), GET /api/eu; GET /api/servidor passa a trazer contas. 404 e erros de cliente do Fastify no formato do contrato.
  • Regras: convite conferido antes de validar e do hash, e de novo na transação; sem código vigente nada passa. Limite e unicidade (sem diferenciar maiúsculas) na mesma transação; primeira conta do banco é admin. Código inicial de CODIGO_CONVITE; depois vale o do banco.
  • Segurança: scrypt N=2^15 r=8 p=1; token de 256 bits, banco guarda SHA-256; cabeçalho Authorization fora do log; 10 tentativas/min por IP (TENTATIVAS_POR_MINUTO; ATRAS_DE_PROXY para IP real atrás do Caddy).
  • App: tela Entrar ("Já tenho conta" / "Tenho um convite") com validação igual à do servidor; sessão em userData cifrada com safeStorage (sem cofre: arquivo 600); reabrir valida em /api/eu e entra direto; 401 volta ao login; sem rede mostra "Sem conexão".
  • Diferenças da técnica: migrations como texto em server/src/db/migracoes.ts (não .sql); validação com JSON schema do Fastify + shared (sem zod).
